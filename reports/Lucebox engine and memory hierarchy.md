# Lucebox Spreads DeepSeek Across Three Memories

Lucebox, the trading name of AGMI AI, Inc., a Milan start-up in Y Combinator's Winter 2027 batch, sells one product, the **Lucebox Zero 495**: the same Ryzen AI MAX+ PRO 495 APU as the Principal's A.T.L.A.S. node, with 128 or 192 GB of LPDDR5X-8533, plus **a 32 GB Radeon AI PRO R9700 on a PCIe 4.0 x4 M.2 riser**, priced **from $6,499**, due for delivery in January–February 2027 and preloaded with Lucebox's own **Apache 2.0 C++/HIP inference engine**. The "383 GB" DeepSeek V4.1 Flash is Lucebox's 2.5-bit `ROCMFP2S` GGUF, and **189 GiB of that 356 GiB file are Engram lookup tables that never enter any memory tier**; they are read row by row from the SSD, and only the remaining ~166 GiB of experts and dense weights are placed by measured use. The R9700 holds the dense weights, the drafter, the KV cache and the roughly 1,000 most-called experts; the APU's integrated GPU holds the next ~9,500 experts, or every remaining expert on the 192 GB model; and on the 128 GB model the coldest ~4,900 experts stream from NVMe through an LRU cache that fetches the next layer's likely experts ahead of time, while a router bias fitted to the box steers tokens toward experts in fast memory. The headline speeds, **up to 49 tok/s writing code on 192 GB, 26 tok/s on 128 GB and about 1,000 tok/s prompt reading**, have not been reproduced by any third party, yet they sit at 55–75% of a bandwidth ceiling, the "without R9700" baseline matches Framework's independent 14–16.5 tok/s, and an independent llama.cpp fork shows the same direction of gain on other MoE models. The caveats are material: the 128 GB figures come from the older Ryzen AI MAX+ 395 build rather than a Zero 495, the 192 GB test rig ran its card at PCIe Gen3 x4 rather than the product's Gen4 x4, decoding is greedy, routing is deliberately biased, and the file behind every speed figure agrees with the reference model's top token only 77.7% of the time and carries no benchmark score. For the node the conclusion is clear: **none of the speed can be reproduced without a discrete GPU**, because the Lucebox engine has no Vulkan backend and no V4.1 profile for the APU alone, mainline llama.cpp still cannot run V4.1, and the only measured V4.1 path on the node's exact APU is DwarfStar at about 14–16 tok/s with a 2-bit file. Under the Principal's precision-first rule, the lossless DeepSeek V4 Flash 0731 should therefore stay the Apex engine, V4.1 belongs in a sealed ROCm-container trial, and an R9700 is worth buying only if that trial shows V4.1's quality lead survives 2-bit quantisation.

Third, the FAQ's one-line statement that "Internet is only needed for updates and the optional cloud fallback". The site never defines that cloud fallback ([home FAQ](https://www.lucebox.com/#faq)).

## Five launch profiles decide how each catalogue model actually runs

The engine is Lucebox's own code, not a llama.cpp server fork in the usual sense. It is a C++17 server (`luce_server`) with its own model graphs, built on a forked, vendored ggml tensor library ("Source repository: https://github.com/Luce-Org/lucebox-ggml; Source base branch: `luce-dflash`"). It compiles ggml's CUDA backend for HIP so that one binary serves both AMD GPUs ([VENDOR.md](https://github.com/Luce-Org/lucebox/blob/main/server/deps/llama.cpp/VENDOR.md)). The build file admits only two backends ("GPU backend to build: cuda or hip") and states "**No BLAS, no Metal, no Vulkan**" ([CMakeLists.txt](https://github.com/Luce-Org/lucebox/blob/main/server/CMakeLists.txt)). It reads standard GGUF and adds three custom quantisation types, ROCMFP2 (type 107), ROCMFPX (104) and MXFP8 (117).

Its speed comes from a family of named techniques. **DFlash and DFlash2** use a separate drafter that "Guesses a block of up to 16 tokens"; **DSpark** uses DeepSeek's own built-in draft block, which Lucebox verifies "bit-identical to plain decode"; **PFlash** reads only part of a long prompt and is labelled "Lossy" on the Engine page; **KVFlash** pages cold KV-cache chunks out to host memory; **Spark** swaps inactive experts in and out on small GPUs; and tool-prefix caching and paged-KV continuous batching serve agent loops and several users ([Engine](https://www.lucebox.com/engine)).

Exactly five launch profiles exist in the code: `ds4-strix`, `ds4-r9700-strix`, `ds41-lucebox`, `ds41-gorgon` and `qwen-next-r9700-strix` ([launch_profiles.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/server/launch_profiles.h)). The table maps each model card on the Engine page to how it really runs. Lucebox labels the card sizes "GB", but they are **GiB of all the model's files**, drafters included. For example, V4.1's "368.4 GB" is 356.42 + 7.42 + 4.58 GiB, which is 395.6 GB on disk.

Three findings from this table matter for anyone judging the box.

First, **the most prominent DeepSeek number on the site does not describe the model it ships.** The "54 tok/s" links to the July post. That post measured "Its 102.3 GB ROCmFPX build" with "four routed experts per token", and said "comparison with the six-expert reference configuration was outside the scope". Lucebox's own documentation, measured on 5 August, found that four experts on the **shipped adaptive 0731 file** cut exact-copy fidelity from 95.0% to **60.0%**, with degenerate output such as `" 0 0 0 0 0 ..."`. It warned that "on an adaptive artifact the same setting costs 35 points of exact-copy fidelity" ([DS4.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS4.md)). The 788 tok/s prefill appears in no post. Its only other source is the repository README, which pairs it with "**86 tok/s** decode" ([README](https://github.com/Luce-Org/lucebox/blob/main/README.md)).

Second, **concurrency switches off the fast paths.** "Paged serving decodes autoregressively: it rejects `--draft`", and for V4.1 "the TP tuning switches of the profile are refused with it" ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)). Every V4.1 speed on the site is therefore one user at a time. That suits the Principal's decision to run Ren and Arthur one after the other rather than together.

Third, **for DeepSeek V4 Flash the R9700 barely helps at the model's native six experts.** The APU-only profile `ds4-strix` measured "8K 320 / 42 prefill / decode tok/s, 123K 284 / 36, code and math suites 39 tok/s at q5, prose 25 at q2" on a 128 GB Ryzen AI MAX+ 395 with no card ([DS4.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS4.md); [RECOMMENDED_SETUPS.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/RECOMMENDED_SETUPS.md)). The dual-GPU profile measured 36–42 tok/s. The card pays off for V4.1 and Qwen3.8-Flash-Next, for the reason explained next.

## Only 166 of the 356 GiB ever enter the memory hierarchy

### The 383 GB file is mostly lookup tables

DeepSeek V4.1 Flash is a "multimodal Mixture-of-Experts (MoE) model with 552B backbone parameters". It has "1 shared expert and 384 routed experts per MoE layer, activating 6 routed experts per token" across 40 layers. Its 20-layer encoder and 20-layer decoder activate "**8B parameters per token during prefill** and **16B during decode**". Beside that sits "Engram conditional memory (196B parameters, sparsely accessed via token-based lookup)", and the model is MIT-licensed with a one-million-token context ([DeepSeek card](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)). Each token reads 6 experts in each of 40 layers, 240 expert reads in all. Each expert has 3 × 5,120 × 2,304 = 35.4 million weights ([config.json](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/raw/main/config.json)), so at 2.5 bits an expert is 11.06 MB.

Lucebox's "383 GB model" is the file `DeepSeek-V4.1-Flash-ROCMFP2S.gguf`: 382,700,617,728 bytes, or **356.42 GiB** ([HF tree](https://huggingface.co/api/models/Lucebox/DeepSeek-V4.1-Flash-ROCMFP23-GGUF/tree/main?recursive=true)). Its engine documentation is blunt about what that file holds: "The ROCMFP2S file is 383 GB: 158 GiB of routed experts, 8 GiB of dense weights and 189 GiB of Engram tables. **The tables are read from the file row by row and never mapped.**" ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)). A direct read of the file header gives the exact split.

| Part of the 383 GB file | Size | Format | Where it lives |
|---|---:|---|---|
| Routed experts (15,360 = 40 layers × 384) | 158.20 GiB | ROCMFP2, "10 bytes per 32 weights, 2.5 bits, codebook {-1, 0, 1, 2} x a ue4m3 scale per 16 weights", with a sign-flip bit | Split across the R9700, the iGPU and (128 GB only) the SSD |
| Engram tables (layers 1 and 14) | 188.83 GiB | 8-bit rows of 264 bytes | In the file on the SSD on both models, read by `pread` |
| Attention, indexer and related | 5.17 GiB | Mostly Q8_0 | R9700 |
| Shared expert | 1.40 GiB | Q8_0 | R9700 |
| Token embedding | 1.23 GiB | F16 (a row lookup) | Not stated by Lucebox |
| Output head | 0.66 GiB | Q8_0 | R9700 |
| Engram projections, other | 0.92 GiB | F16 and small tensors | R9700 |

Sources: [HF card](https://huggingface.co/Lucebox/DeepSeek-V4.1-Flash-ROCMFP23-GGUF) and the file header. The file is text-only, because Lucebox refuses `--mmproj` for V4.1. It also excludes the draft model, which ships separately as a 4.9 GB or 8.0 GB "DSpark" file ([DSpark card](https://huggingface.co/Lucebox/DeepSeek-V4.1-Flash-DSpark-GGUF)).

**The Principal's summary is Lucebox's lead sentence word for word, and it is accurate as a quotation.** It is incomplete as a description. About 53% of the "383 GB" sits outside the three tiers, and the site never mentions Engram. Engram costs little at run time. Each token reads 24 hashed rows in each of the two Engram layers, about 12.7 KB, and DeepSeek designed the tables so that "deterministic addressing enables runtime prefetching from host memory, incurring negligible overhead" ([Engram paper](https://arxiv.org/abs/2601.07372)).

### Three tiers, placed by how often each expert is called

Lucebox's organising sentence is "**Each expert sits where its use pays for it.**" MoE routing is skewed. With a 4K-token prompt on the 128 GB machine, "the R9700 holds 6% of the experts and serves almost a quarter of the calls, while the SSD holds a third of them and serves less than a tenth" ([V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)). The diagram shows one decode step through one MoE layer.

|---|---|---|---|

Sources: [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md), [launch_profiles.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/server/launch_profiles.h) and the chart text in the [V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy). The 960 + 9,495 + 4,905 experts add up to exactly 15,360.

Both GPUs compute at the same time; neither is only storage. Lucebox calls the design "**route-level expert parallelism, not layer pipelining or a second server process**" ([DS4.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS4.md)). "Each expert lives on one GPU. At every layer both GPUs run the experts they hold, then the R9700 combines the results." The July post explains why the obvious alternatives fail: tensor parallelism needs matched GPUs, and a layer split makes "Every token … cross one device, then the other" ([V4 post](https://www.lucebox.com/blog/deepseek-v4-asymmetric-parallelism)).

The CPU only orchestrates. Its threads load experts from the SSD and run a "resolver thread (`MoeStreamedMailbox`)" that serves the GPU graph's requests for streamed experts. During prefill on 192 GB the two GPUs overlap: "While the Ryzen AI MAX+ works on the experts of one band, the R9700 already runs attention for the next. The running state stays on the R9700. It no longer crosses the PCIe link between layers." ([V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)).

The link carries little data. A verify pass moves about 3.7 MB of layer inputs and outputs across it, roughly 0.5 ms at Gen4 x4 or 0.9 ms at Gen3 x4 against a step of about 80 ms (computed). **The x4 riser is a latency problem, not a bandwidth problem**, which is why Lucebox's optimisations cut crossings rather than bytes. The KV cache is not a placement problem either. V4.1 compresses and shares it across layers, so 131,072 tokens need only about 0.3 GiB of F16 rows (computed). The R9700's 32 GB is still tight. On 192 GB, dense weights, hot experts and drafter take about 24.4 GiB, leaving roughly 5–6 GiB for KV, compute buffers and 4,096-token prompt chunks (computed). Lucebox has added an opt-in switch, `LUCE_DS4_DRAFT_SWAP=1`, that "moves the drafter off the R9700 during prefills over 10K tokens to make room for larger chunks" ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)).

### Six mechanisms turned under 1 tok/s into 26

The V4.1 post records how the 128 GB result was built: "Our first version kept the hottest experts on the R9700 and read the rest from the SSD. It gave the right answers, at under one token a second." Its chart then reads "+ unified memory ~3 tok/s → + ranked placement ~4 → + expert cache ~9 → + fused + DSpark ~11 → + pinned memory ~23 → + Lucebox placement ~26 tok/s" ([V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)). The engine documentation spells out each mechanism.

**Ranked, per-box placement.** A placement file assigns each expert "one of `"primary"`, `"secondary"`, `"stream"`". "Each device keeps what fits its budget and demotes the rest one tier", with the least-used experts demoted first according to a routing profile. Users can learn their own profile with `LUCE_DS4_ROUTING_STATS_OUT`. The shipped 128 GB file starts with 1,280 / 9,561 / 4,519 experts, and the budgets demote that to the logged 960 / 9,495 / 4,905. The **192 GB fitted layout is not published** in the repository or on Hugging Face. Lucebox's dashboard installs it ([DSpark card](https://huggingface.co/Lucebox/DeepSeek-V4.1-Flash-DSpark-GGUF)), so a third party cannot reproduce the 192 GB numbers exactly from public files.

**Expert cache and look-ahead.** Streamed experts pass through "a fixed pool of expert slots on the Strix Halo", and "Slots are recycled least recently used first". "Misses load on four loader threads; while layer L routes, the graph also predicts layer L+1's experts from the same input and prefetches them (the prediction only moves bytes early, never the answer)." After load, a usage profile warms the pool in the background. "Prompts of 256 tokens or more load in bulk mode with `O_DIRECT`", so they bypass the page cache ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md); [moe_hybrid_expert_cache.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/common/moe_hybrid_expert_cache.h)).

**Fused graph and DSpark.** "Each decode step runs as one graph across the three tiers, and the DSpark drafter proposes tokens that the model checks in one pass." The drafter is "the draft block DeepSeek ships inside the checkpoint", and verification is "bit-identical to plain decode" ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)).

**Pinned memory.** This was the biggest single step, from about 11 to about 23 tok/s. "The Strix GPU reads all of its unified memory at the same speed, so past its carve the stack continues in locked host memory." The lock is not optional. "With the default 8 MiB lock limit the host tier stays empty … and those experts stream from the SSD instead". Locking is required because "the GPU does not mark host pages as accessed, so unlocked pages were reclaimed and every swap-in evicted all GPU queues of the process" ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)).

**Router bias and protected experts.** A table of 40 × 384 floating-point values is "added once to each layer's selection bias. It steers selection toward the R9700 and away from SSD experts (SSD calls 3.8% -> 0.5% on calibration traffic) without changing mixing weights." Eighty "protected" experts, 51 of them in layers 36–39, are exempt. "A token whose unbiased top-k holds a protected expert keeps that selection, and protected experts always live on the R9700." The post describes the effect plainly: "the router picks the expert in fast memory when two choices are close" ([V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)).

**Layer-major prefill.** The 128 GB profile "reads prompts in 4K-token chunks and runs consecutive chunks layer by layer, so each expert from the SSD is read once per pass instead of once per chunk". Start-up uses the same streaming. "About 120 GB of the model is read before the first token … on eight threads straight from the SSD, past the operating system's file cache … ready in under a minute, down from five."

### On 192 GB the SSD tier disappears for experts, not for Engram

"The 192 GB model has room for all of the experts … around 150 GB, so nothing comes from the SSD while the model runs." ([V4.1 post](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)). That statement is true of experts. **It is literally false for Engram.** After about 146.5 GiB of experts are pinned for the iGPU, roughly 28–33 GiB remains for the page cache. At most 15–17% of the 189 GiB of Engram tables can stay cached, and the rest comes off the drive (computed). The speed cost is small, about 0.2 GB/s of random reads even at 1,000 prompt tokens a second.

The 192 GB profile also turns on DeepSeek's "decoder SWA bounded replay", which Lucebox labels "approximate by design as in the V4.1 report". With it, most prompt tokens pass through only the 20 encoder layers. The profile keeps two other documented departures from the reference: "compressed KV rows stay F16 where the reference stores FP4, and index scores are F32 where the reference rounds them to BF16 (near ties can pick another row)". It also serves the model text-only at 131,072 tokens, against the native one million ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)).

Lucebox refuses CUDA builds of V4.1 ("on sm_121 the candidate-block selection differs from the reference"), layer split and vision. Its two V4.1 profiles both assume an R9700 as the main device and the iGPU as the expert device.

## Every published figure is self-reported, and nearly all fit the physics

**No third party has reproduced any Lucebox DeepSeek V4.1 figure.** No Zero 495 has shipped. The 15 runs on the PRO 495 ("Gorgon Halo") at local-llm-benchmarks.dev include no hybrid and no Lucebox engine ([results.json](https://local-llm-benchmarks.dev/data/results.json)), and the press only repeats Lucebox's numbers. Three independent sources still constrain the claims. The first is **Framework's baseline**: its own 192 GB PRO 495 run with DwarfStar and antirez's Q2 file stayed "close to 14 tokens per second" without speculation, and with DSpark it was 16 percent faster at the start, 20 percent faster at 32K and 19 percent faster at 64K ([Framework blog](https://frame.work/blog/what-192gb-changes-for-local-ai-on-the-framework-desktop)). Its table shows tg 16.3 / 16.5 / 16.5 and pp 350 / 337 / 300 tok/s at 0 / 32K / 64K of existing context ([Framework community](https://community.frame.work/t/85191)), which matches Lucebox's "without the R9700" column, so **the baseline is real**. The second is **an independent hybrid**: the open-source llama-halo-hybrid fork, which pairs a Strix Halo with an R9700 "on an x4 riser", raises Qwen3.8-Flash-Next decode from 47.4 to 65.5–67.3 tok/s (1.40×) and prefill from 937 to 2,265–2,322 tok/s at 7K (2.45×) ([llama-halo-hybrid](https://github.com/sixvolts/llama-halo-hybrid)), the same direction and order as Lucebox's claims. The third is a cautionary multi-GPU build: Level1Techs' "Franken Strix Halo", with two R9700s beside the iGPU, found that the iGPU's "~215 GB/s effective bandwidth becomes the decode bottleneck" for models split by layer, so the iGPU "adds capacity, not throughput" ([Level1Techs](https://forum.level1techs.com/t/franken-strix-halo-2x-r9700s-128gb-strix-halo-unified-memory/254736)). That is exactly the problem Lucebox's per-expert split exists to avoid.

**A bandwidth model reproduces Lucebox's numbers within the limits of the physics.** For the ROCMFP2S file, one single-token pass reads 2.65 GB of routed experts plus 8.74 GB of dense weights, **11.40 GB in all**. The dense part, kept at Q8_0, is three-quarters of every token's reads. That is why moving it to the 640 GB/s card is the main lever for V4.1 and not for V4 Flash.

On the APU alone, everything resident, the ceiling would be 24 tok/s at 273 GB/s. With the R9700 holding the dense part, plain decode tops out at about 45–47 tok/s. With DSpark keeping 4.25 tokens per step on code (the cluster post's figure), the ceiling at 80% bandwidth efficiency is about 72–92 tok/s, and 42–54 tok/s on prose. Lucebox's measured 48.7–54.7 tok/s on code and 31–33 tok/s at 2K–31K therefore land at **roughly 55–75% of ceiling**. Framework's DwarfStar run reached 65% of its own 21.6 tok/s ceiling, so these are ordinary efficiencies, not suspicious ones. All of these ceilings are computed from the file header and published bandwidths.

**Lucebox is a credible engineering shop with an aggressive marketing layer.** On the credible side, it publishes its engine, launch profiles, placement and bias files, KL tables, measured logs and caveats ("Measured by us and rounded … Decode speeds are for the first request after start"). The arithmetic behind every V4.1 figure checks out against independent bandwidth limits and Framework's baseline.

The marketing pages do several things the engineering docs avoid. They lead with a V4 Flash number taken at a setting Lucebox's own docs show degrades the shipped file. They present the box as "160 u" GB of unified memory at 640 GB/s ([cards comparator](https://www.lucebox.com/cards-comparator)), although the July post says "The 32 GB and 128 GB memories are separate, not one shared 160 GB pool" ([V4 post](https://www.lucebox.com/blog/deepseek-v4-asymmetric-parallelism)). They fold figures from the predecessor build into Zero 495 claims, and they carry stale or conflicting counters, terms and dates.

The quality evidence is the weakest link. It rests on an unpublished 177-question internal bench, scored on a different file from the one that produced the speeds. Every V4.1 run also uses a router bias fitted to make that particular box fast.

## Known building blocks, assembled in a way no public system had

Almost every ingredient has prior art. The combination, on consumer AMD silicon, does not. The research found no public system identical to Lucebox's two-GPU expert split, but the search covered only the sources below.

| Lucebox technique | Prior art | Standard or novel |
|---|---|---|

The novel parts are integration work: getting two different AMD GPU generations to share one MoE layer without moving the running state across a four-lane link. The part with the most consequence is the router bias. It is why the box is fast. It is also why "Two boxes don't give exactly the same answer as one box … each setup has its own placement" ([cluster post](https://www.lucebox.com/blog/lucebox-cluster-nic)). Lucebox's "bit-identical" claim compares speculative and plain decoding under the same biased profile, not against DeepSeek's reference routing.

## The node can borrow ideas now and the speed only with a second GPU

### The EVO-X5 Pro can take an R9700 only through a dock or a surrendered drive slot

Lucebox's layout cannot be copied directly. The EVO-X5 Pro has "3 × M.2 2280 Key-M Slots | • SSD1 and SSD2: PCIe 4.0 ×4 | • SSD3: PCIe 4.0 ×1", no PCIe slot and no OCuLink. Its rear has "2 × USB4 v2 (80Gbps…)", and it runs from a "19.5V / 16.9A (330W)" brick ([GMKtec](https://www.gmktec.com/products/gmktec-evo-x5-pro-amd-ryzen-ai-max-pro-495-ai-mini-pc)). Both four-lane slots hold A.T.L.A.S. drives: the 8 TB model drive and the 4 TB OS drive ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L82)).

An M.2-to-x16 riser like Lucebox's therefore means moving one drive to the x1 slot (about 1.97 GB/s). A riser in that x1 slot instead would give the card half the Gen3 x4 link Lucebox measured on. In either case the full-length 300 W card sits outside the 221 × 80 × 195 mm chassis on its own supply.

**A USB4 v2 dock is the only path that keeps both four-lane drives.** Its measured rates are close to Lucebox's test rig. A Thunderbolt 5 dock on a Strix Halo moved "3.8 GB/s each way" between the card and the iGPU over a 40 Gbps link, against about 6.4 GB/s in a Gen4 x4 slot. One small decode-step copy took 45 µs against 24 µs, and a card in the dock decoded Qwen3.8-Flash-Next at 60.0 tok/s against 58.2 for another card in a Gen4 x4 slot ([USB4 notes](https://github.com/sixvolts/llama-halo-hybrid/blob/HEAD/halo-cookbook/usb4-thunderbolt.md)).

Applied to V4.1's roughly 80 transfers per verify step, the extra latency costs about 2% (computed). The same source lists hard requirements: "`thunderbolt.host_reset=false`", the dock "plugged in and powered before the box boots", and "`amdgpu.runpm=0`". Without the first, the card returns with a 256 MB window and "ROCm reports no peer access from the iGPU to the card". It also states plainly: "**Not measured: an R9700 or another 32 GB card in the dock**". The hardware cost is the card at about **$1,800** ([Lucebox comparator](https://www.lucebox.com/cards-comparator)), a dock, and a supply of at least 750 W ([AMD](https://www.amd.com/en/products/graphics/workstations/radeon-ai-pro/ai-9000-series/amd-radeon-ai-pro-r9700.html)).

### No engine runs V4.1 on the node's Vulkan stack today

The node runs llama.cpp v0.4.1 on Vulkan, and the host has no ROCm ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L143)). Every route to V4.1 leaves that stack. **The Lucebox engine** builds only for CUDA or HIP, and both its V4.1 profiles set `--target-device hip:0` (the R9700) and `--expert-device hip:1` (the iGPU) ([launch_profiles.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/server/launch_profiles.h)); it was validated on ROCm 7.2.x, nobody has reported it on the ROCm 10.x that AMD lists for Ubuntu 26.04.1 ([ROCm matrix](https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html)), and although its code does not refuse a single-device V4.1 run, no such run is documented or measured anywhere. **Mainline llama.cpp** has no `deepseek41` architecture at v0.4.1, at v0.5.0 or on master; PR #28696 is still open with "At least 2 approving reviews are required to merge", has been tested only on CPU and CUDA, is capped near 16K context, and adds no backend kernels ([PR #28696](https://github.com/ggml-org/llama.cpp/pull/28696)). **ik_llama.cpp** merged V4.1 on 21 September, but that project supports CPU and CUDA only, so on the node it would be an unmeasured CPU path ([ik_llama.cpp PR 2455](https://github.com/ikawrakow/ik_llama.cpp/pull/2455)). **DwarfStar**, antirez's dedicated DeepSeek engine, is the only one with an independent V4.1 measurement on this exact APU, running in kyuz0's ROCm 10.0 container built "for Strix Halo (`gfx1151`)" ([kyuz0 toolbox](https://github.com/kyuz0/strix-halo-ds4-toolbox)).

The node already has a pattern for this. Its Phase 4 engines run "ROCm inside containers" ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L145)) so that "the host never needs a ROCm install" ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L147)). Its kernel line already sets `amdgpu.gttsize=196608` (192 GiB) ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L126)), above the 176 GiB Lucebox needs.

### Quantisation decides the case before speed does

The Principal's standard is top results, not top speed, and quantisation is where V4.1 struggles on a 192 GB box. At full precision V4.1 Flash leads V4 Flash 0731 on Artificial Analysis by **39.46 to 34.33**. Most of the gain is in agentic terminal work and automation ([AA V4.1](https://artificialanalysis.ai/models/deepseek-v4-1-flash); [AA V4](https://artificialanalysis.ai/models/deepseek-v4-flash)). Every V4.1 file that fits the node is a 2–3-bit quantisation. The node's engine budget is ~164 GiB ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L231)); assume about 8 GiB of it goes to KV cache, buffers and drafter, leaving ~156 GiB for weights.

Resident weights exclude the 188.83 GiB of Engram tables, which every engine reads from disk.

A V4.1 file that agrees with its reference model's top token only 78% of the time is in a different fidelity class from a lossless 0731. The Qwen 3.8 27B file that Lucebox serves, Unsloth's UD-IQ4_XS, reaches "mean KL divergence 0.018, 94% top-1 agreement" by comparison ([Qwen 3.8 post](https://www.lucebox.com/blog/qwen38-r9700)). The two KL methods differ, so the comparison is indicative only. **Whether V4.1's five-point lead survives 2-bit compression has not been measured by anyone.** It is the question that decides whether any of this is worth doing.

### Risks, and what the zero-cloud rule allows

The node's rule is absolute: "No model inference runs anywhere but this node … No hosted AI, no cloud fallback, no telemetry from any installed component" ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L54)). **The Lucebox engine itself passes.** A search of its source at commit 6f2b179 found no telemetry, licence check or vendor endpoint. Its only outbound code is the multi-box cluster socket and an "upstream proxy" forwarder that runs only when `pflash_upstream_base` is set ([repository](https://github.com/Luce-Org/lucebox)).

**The Lucebox appliance software does not pass.** The daily update check, the undefined "optional cloud fallback", the crash-report button and the Tailscale and Connect paths all reach outside the box. None of them is in the public repository, and none is needed to run the engine.

Building any of these engines needs GitHub, Docker Hub and possibly AMD's package servers at build time. The node's allowlist names only "package mirrors during builds, Hugging Face during model pulls" ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L705)), and the node may never "Install software or pull models from outside the allowlist" ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L890)). That is a decision for the Principal.

The operating risks are concrete. **ROCm stability on gfx1151 has a mixed record**: AMD itself "does not recommend installing amdgpu-dkms on APUs such as gfx1151" after page-fault reports ([ROCm #6186](https://github.com/ROCm/ROCm/issues/6186)), so any container must use the inbox driver. **Lucebox's profiles need locked memory**, running as root or with `ulimit -l unlimited`, and they break if compute-wave save/restore is switched off ([DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)). **The engine changes fast**, nearly 2,000 commits in six months, so any adoption must pin a commit and the model files' hashes. **Greedy figures will not match the node's sampling**: Lucebox measured with greedy decoding, while the node samples DeepSeek at temperature 1.0 ([engines.json](../scripts/day1/config/engines.json#L170)), so draft acceptance, and with it speed, has to be measured under the node's own settings. **Disk wear is not a concern**, because streaming experts or Engram rows only reads the drive and SMART's written-data counter counts host writes only ([Netdata](https://www.netdata.cloud/guides/smartctl-disk-monitoring/smartctl-data-units-written-tbw/), excerpt). **An R9700 adds noise and power**: its blower "needs 2,700 to 3,100 RPM to hold 90 C" at 300 W ([fan post](https://www.lucebox.com/blog/fan-forecast)), and with `amdgpu.runpm=0` "the card never powers down at idle" ([cookbook](https://github.com/sixvolts/llama-halo-hybrid/blob/HEAD/halo-cookbook/README.md)).

### What to adopt without new hardware

Some of Lucebox's ideas need no card and no new engine. Usage-ranked expert placement is the design to follow if the node ever adds a card; llama.cpp's `-ot` tensor overrides are its manual form. Manage's memory guard, which "stops the program filling it before the box can freeze" ([Manage demo](https://www.lucebox.com/manage-demo.html)), mirrors what the node's Arbiter already does with its fixed 16 GiB host reserve ([DOC](../docs/ATLAS_FRAMEWORK_REVIEW.md#L1189)). Signed release manifests that expire after 120 days ([System](https://www.lucebox.com/system)) are a cheap discipline for the node's own pinned images. Lucebox's "Learning", stripped of marketing, is retrieval of relevant past work from local agent session logs, which fits the node's existing retrieval stack. Single-stream speculative decoding pays off precisely because Ren and Arthur run one after the other rather than together. None of these needs Lucebox software, and none changes the repository today.

## Conclusion

Lucebox is a heterogeneous-memory engine with a box built around it, not mainly a hardware company. Its real discovery is narrow and useful. In DeepSeek V4.1 Flash as Lucebox and antirez quantise it, with the dense weights kept at 8 bits, three-quarters of each token's memory traffic is the dense part, not the experts. Putting that part on a cheap 640 GB/s card over a four-lane link, and letting the APU's own GPU compute the experts it holds, roughly triples prompt reading and doubles decode. A fitted router bias then buys the last increment by steering tokens toward fast memory, at the cost of matching the reference model exactly. The same physics explains why the card barely helps DeepSeek V4 Flash, whose dense part is light. It also explains why the Principal's node, which lacks the card, sits at or below about 14–16 tok/s on V4.1 with every engine and file examined.

The research changes the question the Principal faces. The question is no longer "can the node run the 383 GB model?". It can, slowly, in a container, at about 2.5 bits. The question is whether DeepSeek's five-point lead at full precision survives that compression, against a 0731 model the node can run without any loss at all. Nobody has measured that. A short trial on the node's own tasks answers it for the cost of disk space and an allowlist change. The trial should come before any money is spent on an R9700, since the card's tripling of speed is worth paying for only if the quality is there to be accelerated.
