## Gaps closed

1. **The Engine page's 368.4 GB (row 8).** The site states every model-card size as GiB of all its files, labelled "GB". For V4.1 that is ROCMFP2S plus both drafters: 368.42 GiB, which is 395.6 GB on disk. The blog's "about 390 GB" download equals ROCMFP2S plus the MXFP4-Q8 drafter (390.67 GB).
2. **SSD-tier cache policy (row 15).** The cache is LRU. Prediction-based prefetch and warm-start loads never evict a slot that a pending evaluation or a request needs. Bulk prefill loads bypass the page cache and recycle within half the pool.
3. **Contents of the shipped 128 GB layout.** `placement_lucebox.json` assigns 1,280 experts as primary, 9,561 as secondary and 4,519 as stream. The budgets then demote one tier at a time. 1,280 experts would need 13.18 GiB, but the 10,500 MiB budget holds about 995. The log ends at 960 / 9,495 / 4,905: 320 primary experts moved down, then 386 secondary ones moved down (4,519 + 386 = 4,905). `massive_experts.json` protects 80 experts, 51 of them in layers 36-39. The router bias has 15,360 f32 values, 12,017 of them non-zero, ranging from −4.50 to +0.11. The 192 GB fitted layout is not published anywhere (row 17), so a third party cannot reproduce the 192 GB numbers exactly from public files.
4. **llama.cpp PR #28696 (rows 9-10).** It was re-read on 2026-10-15: still open and unmerged, so nothing changes for the v0.4.1 pin. The FP4-experts reading of the "Q8_0 staging" file is now supported by a byte-level match with smalinin's MXFP4 GGUF.
5. **No APU-only V4.1 path in the Lucebox engine.** `launch_profiles.h` defines exactly five profiles: `ds4-strix`, `ds4-r9700-strix`, `ds41-lucebox`, `ds41-gorgon` and `qwen-next-r9700-strix`. Only V4 (not V4.1) has a single-Strix-Halo profile. DS41.md refuses "V4 fused decode, `--ds4-fused-verify-f16-kv` on one GPU" for V4.1. For A.T.L.A.S., which has no discrete GPU, Lucebox's V4.1 recipe is not a documented option.
6. **Inconsistencies on the site that the notes missed.** (a) The blog's 192 GB "Run it" command passes `--draft DeepSeek-V4.1-Flash-DSpark-draft-MXFP4-Q8.gguf`. Yet the post itself, DS41.md, the drafter card and the cluster post all say the 192 GB runs used the smaller Q2K-Q4K drafter (about 5 GB). The notes' R9700-occupancy arithmetic correctly assumes Q2K-Q4K. (b) DS41.md still calls the Q2K-Q4K drafter "not published", but it has been on Hugging Face since at least 2026-10-06.
7. **Context for the ROCm-vs-Vulkan post (row 25).** The "v0.7.5" belongs to a third-party Strix Halo fork. The comparison used different quantisations, the V4 model and the APU alone.

## Gaps still open

- **Earlier versions of the pages.** The Wayback Machine is still unreachable: curl gets connection resets and WebFetch refuses the domain. Earlier versions of the V4.1 post (published 2026-09-29, modified 2026-10-06) and of the Engine page cannot be compared.
- **Framework's chart values (row 23)** are in an image only.
- **R9700 FP16 peak (row 26).** AMD's spec page returned 503, so the 191 TFLOPS figure lacks a primary source.
- **Engram tensor type in the PR's Q2_K file.** It is not stated on the PR page. The notes' arithmetic (Engram at about 2-3 bits) remains an inference.
- **Missing performance data.** No per-tier call split is published for the 192 GB machine, and no plain (no-drafter) V4.1 decode figure. There are no measurements on a 128 GB Zero 495 (only the 395 build), no hard-bench score for ROCMFP2S itself, and no decode figures beyond about 31K context.
- **Production PCIe link.** Lucebox does not say whether the Zero 495's riser trains at Gen4 x4; the 192 GB test box ran at Gen3 x4.
- **Scope.** This file covers only how V4.1 runs. The Engine page also offers Qwen3.8-Flash-Next (106.3 GiB, "R9700 + Strix Halo, 4 at once", profile `qwen-next-r9700-strix`), which is on the Principal's list. The other offered models are covered in `lucebox_site_and_offering.md`, not here.
