## Key question 1: The model file — what exactly is the 383 GB artefact, and how does it relate to the llama.cpp conversion sizes?

### Takeaway
The "383 GB model" is Lucebox's own GGUF `DeepSeek-V4.1-Flash-ROCMFP2S.gguf` (382,700,617,728 bytes = 382.70 GB = 356.42 GiB): 2.5-bit routed experts (158 GiB), Q8_0 dense weights (8 GiB) and DeepSeek's two Engram lookup tables kept at their native 8-bit row encoding (189 GiB). It is text-only (no vision encoder) and does not contain the MTP/DSpark head, which ships as a separate 4.9 GB or 8.0 GB drafter file. More than half of the 383 GB is Engram tables that are never placed in any memory tier; they are read from the file row by row. So the Principal's summary matches the blog's wording exactly, but the expert-placement story covers only about 166 GiB of the file.

### Inferences
- Calculation (config.json): one routed expert = 3 × 5120 × 2304 = 35,389,440 weights; all routed experts = 40 × 384 × 35.39M = 543.6B weights. That plus ~7.8B dense weights is about 551B, which matches DeepSeek's "552B backbone". Engram = 768,022,850 rows × 256 = 196.6B, which matches "196B parameters".
- Calculation: at 2.5 bits per weight, one ROCMFP2S expert is 11.06 MB (10.55 MiB), and all 15,360 experts take 158.2 GiB. This matches DS41.md's "158 GiB" and the load log's 9.89 GiB / 960 experts = 10.55 MiB per expert. The native FP4 experts (4.25 bits with ue8m0 scales) would take 268.9 GiB, which matches the HF card's teacher "269 GiB".
- Calculation: Engram = 768,022,850 rows × 264 bytes (256 e4m3 bytes plus 8 e8m0 scale bytes per row) = 202.76 GB = 188.83 GiB. This matches "189 GiB of Engram tables". So 158 + 8 + 188.8 = 354.8 GiB, and the other ~1.6 GiB of the 356.42 GiB file is small F16/F32 tensors and metadata.
- Calculation: the parts that are actually placed across the R9700, unified memory and SSD are the experts plus the dense weights, ≈ 166 GiB (≈ 178 GB). About 53% of the "383 GB" (the Engram tables) is file-resident and read by row lookup on every model size.
- Inference: the llama.cpp PR's Q2_K (246.3 GiB) is ~110 GiB smaller than ROCMFP2S, although Q2_K experts alone (≈2.625 bpw ≈ 166 GiB) are larger than ROCMFP2S experts. The difference only works out if the PR's Q2_K also quantizes the Engram tables to roughly 2-3 bits (196.6B × 2.625/8 ≈ 60 GiB). This is unverified arithmetic. Lucebox, antirez (365.7 GB) and the other ~366 GB files keep Engram at ~8 bits, which explains their size.
- Inference: the PR's "Q8_0 staging file 507.9 GB" is close to the 510.3 GB native checkpoint. All-Q8_0 would be ≈ 586 GB for the backbone alone, so the staging file probably keeps the experts at native FP4. This is unverified.
- Note: Lucebox's speed claims are measured on ROCMFP2S. Its quality claims (164 of 177) are measured on a different file, `ds41-lucebox-final.gguf`. The blog says so: "ours reads prompts faster, and it is the one measured in this post".

### Gaps
- The Engine page lists DeepSeek V4.1 Flash as "368.4 GB", which matches no published file (ROCMFP2S 382.70 GB / 356.42 GiB; final 366.13 GB). One arithmetic coincidence: ROCMFP2S (356.42 GiB) plus both drafters (7.42 + 4.58 GiB) = 368.42 GiB. This is unconfirmed. — [Engine page](https://www.lucebox.com/engine)
- The per-tensor quantisation inside `ds41-lucebox-final.gguf` (which layers get IQ3_XXS) is not published beyond "Each layer mixes the standard IQ2 and IQ3 formats, within the size of antirez's Q2".
- The PR #28696 page could not be re-read this session (HTTP 403 via the proxy), so its current state after 14 Oct 2026 is unverified.

## Key question 2: Placement — what lives on the R9700, in unified memory and on the SSD; KV cache; expert caching and prefetch; 128 GB vs 192 GB

### Takeaway
Placement is static, per expert, and decided by measured routing frequency. The R9700 holds all dense weights, the drafter, the KV cache, the sampler and about 1,000-1,140 of the hottest experts (≈10-12 GiB, about 6-7% of experts serving about a quarter of calls). The iGPU of the APU holds the next tier in its carve-out plus mlock'ed host memory. On the 128 GB machine the remaining ≈32% of experts (50.5 GiB) are streamed from the NVMe SSD through a slot cache in unified memory. That cache uses next-layer prediction and prefetch, a usage-profile warm-up, and an `O_DIRECT` bulk-load path. A per-expert router bias steers routing toward fast tiers, and protected "massive" experts are always on the R9700. On the 192 GB machine every expert is resident: 12,000 MiB on the R9700, about 146-150 GiB on the iGPU, no expert streaming.

### Cited Findings
**Lucebox's wording (blog):**
- 192 GB: "The 192 GB model has room for all of the experts. The R9700 keeps the layers every token goes through, the drafter and the experts used most. The integrated GPU of the Ryzen AI MAX+ keeps all the others, around 150 GB, so nothing comes from the SSD while the model runs." — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)
- 128 GB: "On the 128 GB model the experts no longer all fit in memory, so the SSD becomes a third tier. ... The R9700 reads its 32 GB at 640 GB/s, the integrated GPU reads unified memory at around 240 GB/s, and the SSD holds everything but reads only a few GB a second. DeepSeek V4.1 Flash picks 6 of its 384 experts for every token in each of its 40 layers, so where each expert lives decides how fast the model writes." — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)
- Chart text (inline SVG) for 128 GB at 128K context: "R9700 ; ~10 GB, ~1,000 experts ; 640 GB/s ; Unified memory ; ~100 GB, ~9,000 experts ; ~240 GB/s ; SSD ; ~50 GB, ~5,000 experts ; ~4.5 GB/s". Caption: "Unified memory includes system memory pinned so it is never swapped out." — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)
- "Experts are placed by how often they are used. ... With a 4K-token prompt, the R9700 holds 6% of the experts and serves almost a quarter of the calls, while the SSD holds a third of them and serves less than a tenth." Chart: "R9700 ; 24% of calls ; 6% of experts ; Unified memory ; 68% of calls ; 61% of experts ; SSD ; 9% of calls ; 32% of experts". — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)
- Optimisation steps (blog list and chart): "Unified memory as a second tier"; "Ranked placement. The most used experts go on the fastest tier."; "Expert cache. Experts read from the SSD go through a cache in unified memory, and the next layer's experts are guessed and fetched ahead of time."; "One graph and DSpark"; "Pinned memory. The unified-memory tier grows past the part reserved for the GPU into pinned system memory, which moves thousands of experts off the SSD."; "Placement and routing for this box. The placement is fitted to this machine, and the router picks the expert in fast memory when two choices are close." Chart values: "R9700 + SSD" (the text says "under one token a second") → "+ unified memory ~3 tok/s" → "+ ranked placement ~4" → "+ expert cache ~9" → "+ fused + DSpark ~11" → "+ pinned memory ~23" → "+ Lucebox placement ~26". — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)
- Loading: "On the 128 GB model, about 120 GB of the model is read before the first token: the layers every token uses and the experts kept in memory. The engine reads them on eight threads straight from the SSD, past the operating system's file cache ... The server is ready in under a minute, down from five." — [blog](https://www.lucebox.com/blog/deepseek-v41-lucebox-memory-hierarchy)

**Mechanism (engine docs, primary):**
- Tiers: "**R9700 (primary).** Dense weights, the drafter and the hottest experts. **Strix Halo (secondary).** A second expert stack through the in-process expert parallel path ... The Strix GPU reads all of its unified memory at the same speed, so past its carve the stack continues in locked host memory (`ggml_backend_cuda_set_host_spill`). The host keeps 5 GiB plus one layer-major prefill pass (at most 16,384 prompt tokens) free, whatever `--max-ctx` is. **SSD (streamed).** Everything else, read on demand into a slot cache on the Strix Halo" — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Placement file: "`--ds4-expert-placement placement_lucebox.json`: JSON `{"owners": [...]}`, one of `"primary"`, `"secondary"`, `"stream"` per expert ... Each device keeps what fits its budget and demotes the rest one tier; with a routing profile (`LUCE_DS4_HOTNESS_CSV`, or counts learned with `LUCE_DS4_ROUTING_STATS_OUT`) the least used go first." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Router bias: "f32 `[n_layer][n_expert]`, added once to each layer's selection bias. It steers selection toward the R9700 and away from SSD experts (SSD calls 3.8% -> 0.5% on calibration traffic) without changing mixing weights." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Protected experts: "A token whose unbiased top-k holds a protected expert keeps that selection, and protected experts always live on the R9700." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Load-log example: "expert ownership: primary 960 experts 9.89 GiB, secondary 9495 experts 97.80 GiB, streamed 4905 experts 50.52 GiB" and "decode routed calls: ... streamed 1635 experts, cache hit 93.4% (prefetched 8.6%, warm 0.0%), loaded 423 (266 by prefetch) 4.36 GiB: read 1476 ms, upload 66 ms, wait 664 ms (157 missed, 104 late), compute 0 ms; prefetch accuracy 80.3% of 1635". "`missed` counts streamed experts nobody predicted, `late` those whose prefetch was still loading when the layer needed them." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Streamed cache: "`src/common/moe_hybrid_expert_cache.cpp` keeps a fixed pool of expert slots on the Strix Halo, sized from its free memory after everything else. ... Misses load on four loader threads; while layer L routes, the graph also predicts layer L+1's experts from the same input and prefetches them (the prediction only moves bytes early, never the answer). After load, a usage profile warms the pool in the background. Prompts of 256 tokens or more load in bulk mode with `O_DIRECT`, so they neither pollute nor evict the page cache." In the fused graph "each layer posts its routes to host-mapped memory (`ggml_host_mailbox_post`), a resolver thread (`MoeStreamedMailbox`) pins and loads them". — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- No cache-replacement policy (LRU/LFU) is named. The docs say only "fixed pool of expert slots", prediction-based prefetch, and a background warm-up from a usage profile. — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- 128 GB profile values: "the R9700 as target with 10,500 MiB of experts, the Strix Halo as `--expert-device hip:1` (its budget is automatic), the Lucebox placement, router bias and protected experts, dense batched prefill in 4,096-token chunks, `--max-ctx 131072`". The profile code sets `LUCE_EXPERT_BUDGET_MB=10500`, `--chunk 4096`, `--ds4-prefill dense`, and `share/deepseek41/placement_lucebox.json`, `router_bias_lucebox_40x384_f32.bin`, `massive_experts.json`. — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md), [launch_profiles.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/server/launch_profiles.h)
- Locked memory requirement: "Run it as the `lucebox-model` service (root, so the Strix host tier can be locked) or with `ulimit -l unlimited`: with the default 8 MiB lock limit the host tier stays empty, the load log says so, and those experts stream from the SSD instead." Also: "Locked host memory is `mlock`ed: the GPU does not mark host pages as accessed, so unlocked pages were reclaimed and every swap-in evicted all GPU queues of the process." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- Measured 128 GB box: "R9700 32 GB + Strix Halo (64 GiB carve), 61 GB of host RAM, Crucial P310 NVMe, `--profile ds41-lucebox`". — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- 192 GB profile: "The `ds41-gorgon` profile puts the dense weights, 12,000 MiB of the hottest experts and the drafter on the R9700 (`hip:0`) and every other expert on the iGPU (`--expert-device hip:1`), with the protected experts from `share/deepseek41/massive_experts.json`, 4,096-token prefill chunks and `--max-ctx 131072`." Also: "The iGPU maps about 150 GiB of experts. On Linux, raise its GTT limit with the `amdgpu.gttsize` and `ttm.pages_limit` kernel parameters (180224 and 46137344 on the measured box)." — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- `LUCE_DS4_DRAFT_SWAP=1` (opt-in) "moves the drafter off the R9700 during prefills over 10K tokens to make room for larger chunks". — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md)
- KV cache and sampler on the main GPU: "Both owners are submitted for each MoE layer before an on-device join; the target KV cache and sampler remain on the main GPU. This is route-level expert parallelism, not layer pipelining or a second server process." — [DS4.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS4.md). ### Inferences
- Calculation: the logged split 960 + 9,495 + 4,905 = 15,360 experts (= 40 × 384) is 6.25% / 61.8% / 31.9% of experts. This matches the chart's 6% / 61% / 32%. The SVG's "~10 GB / ~100 GB / ~50 GB" are GiB values (9.89 / 97.80 / 50.52 GiB).
- Calculation: 192 GB placement: 12,000 MiB = 11.72 GiB ≈ 1,138 experts ≈ 7.4% of experts on the R9700, so about 146.5 GiB of experts are on the iGPU ("about 150 GiB"). R9700 occupancy ≈ 8 GiB dense + 11.7 GiB experts + 4.6 GiB drafter (Q2K-Q4K) ≈ 24.3 GiB, which leaves ≈ 7 GiB for KV, compute buffers and 4,096-token prefill chunks. 128 GB: 8 + 10.25 + 7.42 (MXFP4 drafter) ≈ 25.7 GiB.
- Calculation: the GTT values are consistent: `amdgpu.gttsize=180224` MiB = 176 GiB and `ttm.pages_limit=46137344` × 4 KiB = 176 GiB. This is the same 176 GiB cap that the earlier ATLAS notes derived for a 192 GB node.
- Calculation (rough, F16 compressed rows only): V4.1 shares compressed KV across layers (sources 2, 8, 14 at ratio 2 and 20 at ratio 1), ≈ 2.5 rows × 512 × 2 bytes ≈ 2.5 KB per token, or ≈ 0.31 GiB at 131,072 tokens, plus small sliding-window and indexer state. The KV cache is therefore not a placement problem; it fits on the R9700 with large margin. Indexer-key storage was not modelled.
- Inference: "three kinds of memory" is really four placements: R9700 GDDR6, the iGPU's BIOS carve-out, mlock'ed host pages of the same LPDDR5X, and the NVMe. On the 128 GB 395 box the second tier is 64 GiB carve plus ≈34 GiB locked host memory. The biggest single published speed step ("+ pinned memory ~23 tok/s" from ~11) came from extending the second tier into locked host memory.
- Inference: the blog's "nothing comes from the SSD while the model runs" (192 GB) is about experts. The engine reads Engram rows from the GGUF via host file I/O on every path ("never mapped"), so on the 192 GB machine Engram lookups still hit the SSD unless the page cache holds those rows. How much of the 189 GiB of tables the page cache holds when about 176 GiB is pinned for the GPU is not published. Calculation: per token, 2 layers × 24 rows × 264 B ≈ 12.7 KB of payload, or ≈ 48 random 4 KiB reads. At 1,000 prompt tok/s that is ≈ 48K IOPS / ≈ 0.2 GB/s, well inside a P310's rated 1M random-read IOPS (see Key question 4).
- Inference: placement is fitted per box (the "Lucebox placement", plus a `placement.json` / `router_bias.bin` "fitted to this configuration" for 192 GB). It is offline and static, plus a dynamic slot cache only for the SSD tier. No runtime re-placement between the R9700 and the iGPU is documented.

### Gaps
- The cache replacement policy for the SSD slot pool (LRU, LFU or other) and the predictor's exact form ("predicts layer L+1's experts from the same input") are not specified in the docs. The source file `moe_hybrid_expert_cache.cpp` was not read (a shallow clone's lazy blob fetch timed out).
- The 192 GB `placement.json` and `router_bias.bin` used for the published runs are described as "fitted to the box" and not shipped under that name in the HF repos. Whether they are in `server/share/deepseek41/` was not verified (GitHub API refused with 403).

## Key question 3: Compute — which processor computes what, interconnect, and the software stack

### Takeaway
Two GPUs compute, and the CPU only orchestrates. The R9700 (gfx1201) runs attention, dense/shared-expert layers, the hot experts, Engram application (192 GB profile), the DSpark drafter, KV, sampler and the final join. The Radeon 8065S/8060S iGPU (gfx1151) runs the experts it owns, at the same time, on the same layer ("route-level expert parallelism"). CPU threads only load SSD experts and resolve the host mailbox. The link is the R9700 on a PCIe 4.0 x4 M.2-to-x16 riser in the product spec, but the 192 GB measurements were taken on PCIe Gen3 x4. It is not OCuLink and not USB4. The software is Lucebox's own open-source C++ server (`luce_server`, Apache 2.0) on a forked, vendored ggml snapshot with HIP kernels (ROCm 7.2), not Vulkan, and not a llama.cpp/ik_llama.cpp/vLLM/KTransformers deployment.

### Inferences
- Calculation (PCIe traffic, decode): per verify pass of 6 tokens × 40 layers, the iGPU expert input (8-bit, 5,120 B) plus output (bf16, 10,240 B) is ≈ 3.7 MB. That takes ≈ 0.47 ms on Gen4 x4 (≈7.9 GB/s) and ≈ 0.94 ms on Gen3 x4 (≈3.9 GB/s), plus about 80 small transfers of latency per pass. This is a few percent of a ≈ 80 ms pass. The PCIe link is latency-sensitive, not bandwidth-bound, which is why Lucebox's optimisations target fewer crossings rather than bytes.
- Calculation (PCIe, prefill at 1,000 tok/s × 40 layers × ~15 KB): ≈ 0.6 GB/s, so a x4 link is not the prefill bottleneck either.
- Inference: the published 192 GB measurement box ran the R9700 at PCIe Gen3 x4 while the product spec says PCIe 4.0 x4. Either the test machine was not the production Zero 495 board or the link trained at Gen3. Lucebox does not say which. Given the calculation above, the difference should matter little for these figures.
- Inference: Lucebox is best described as its own engine with its own model code, built on a forked ggml tensor library (via Luce-Org/lucebox-ggml), using ggml's CUDA backend compiled for HIP/ROCm. It is not a llama.cpp server fork in the usual sense. It shares GGUF and ggml types with llama.cpp and adds custom types (ROCMFP2 type 107, ROCMFPX type 104, MXFP8 type 117).
- Inference: the 128 GB `ds41-lucebox` profile does not set `LUCE_DS41_DECODER_BOUNDED_REPLAY`, while `ds41-gorgon` does. The 192 GB prefill figures therefore benefit from DeepSeek's sanctioned approximation (most prompt tokens pass only the 20 encoder layers), and the 128 GB figures do not. Framework's baseline also enabled bounded replay (see Key question 4).

## Key question 4: Performance — every published figure, and whether it is physically plausible

### Takeaway
On the 192 GB machine Lucebox publishes about 49 tok/s decode on code (48.7-49.5 measured; 54.7 tok/s in the later cluster post), about 31-33 tok/s at 2K-31K context, and about 750-1,040 tok/s prefill, all with the DSpark drafter. On the 128 GB machine (actually a Ryzen AI MAX+ 395 build) it publishes about 26 tok/s on code, 14-17 tok/s at 4K-21K context and about 120 tok/s prefill. A bandwidth model puts the 192 GB numbers at roughly 50-65% of the achievable ceiling, and the 128 GB decode needs an SSD-tier cache hit rate of about 90% or more (their log shows 93.4%). All figures are physically plausible. The "3x" comparison mixes different quantisations, engines and prompt shapes, and the quality and speed figures come from different files.

### Inferences
All in this subsection are my calculations from config.json, the file sizes and the bandwidths above. They are not Lucebox claims.

- Bytes per token (ROCMFP2S): routed = 6 × 40 × 11.06 MB = **2.65 GB**. Dense read per forward pass = 8 GiB − 0.70 GB embedding table ≈ **7.9 GB** (attention, shared expert, compressors/indexer, 0.70 GB output head; the cluster post confirms "the model's 703 MB output matrix"). Total ≈ **10.5 GB per single-token pass**. Dense weights dominate, which is why putting them on the 640 GB/s R9700 is the main lever.
- iGPU-only ceiling (the "without R9700" case): ≈ 10.5 GB / 273 GB/s = 38.6 ms, about 26 tok/s at 100% of peak, or ≈ 21 tok/s at 80%. antirez's Q2 is a little smaller per token (≈2.39 GB routed). Framework measured 14 plain / 16.3-16.5 with DSpark, which is consistent with ~55-70% efficiency.
- R9700 + iGPU single-token ceiling (192 GB, hot share h ≈ 0.24-0.30 of calls): R9700 dense ≈ 12.3 ms at peak (15.4 ms at 80%) followed by the MoE step, where the iGPU's ≈ 1.9 GB takes 6.8-9.3 ms, in parallel with the R9700's hot experts. That gives ≈ 19-25 ms, or **≈ 40-52 tok/s plain-decode ceiling**. Lucebox does not publish a plain-decode V4.1 figure.
- With DSpark (verify width 5-6 tokens; cluster post: 4.25 tokens kept per step on code, 2.5 on prose): a verify pass touching 18-24 distinct experts per layer reads ≈ 8-10.6 GB of experts. At 80% bandwidth that is ≈ 42-51 ms per pass, a **ceiling of ≈ 83-101 tok/s on code and ≈ 49-59 tok/s on prose**. Measured 49-55 tok/s (code) and 31-37 tok/s (prose/2K) are ≈ 55-65% of these ceilings. **Plausible.** Implied single-box step at 54.7 tok/s × 4.25 kept is ≈ 78 ms.
- 192 GB prefill ≈ 1,000 tok/s: with bounded replay most prompt tokens use ≈ 8B active parameters, so ≈ 16 GFLOP/token, or ≈ 16 TFLOPS for matmuls (≈ 32 TFLOPS without replay). That is well under the R9700's stated matrix peak (191 TFLOPS FP16 per Lucebox; 95.7 TFLOPS vector per Puget) plus the iGPU's share. Weight traffic per 4,096-token band (≈ 146 GiB of iGPU experts at ≈ 218 GB/s ≈ 0.7 s) is far from binding, and PCIe traffic is ≈ 0.6 GB/s. **Plausible.** The bound is kernel efficiency, not bandwidth.
- 128 GB decode 26 tok/s: if 9% of the 240 routed calls per token (≈ 21.6 calls, ≈ 239 MB) all came from the SSD at 4.5 GB/s, that alone is 53 ms/token, so ≤ 19 tok/s even with nothing else running. The published 26 tok/s therefore **requires the SSD-tier slot cache to hit**. At a 90% hit rate, misses cost ≈ 24 MB ≈ 5-8 ms per token, and at the logged 93.4% ≈ 16 MB ≈ 3.5-5 ms. The router bias (SSD calls "3.8% -> 0.5%" on calibration traffic, ≈ 1.2 calls/token) makes this easier. The log's measured read rate (4.36 GiB in 1,476 ms ≈ 2.95 GiB/s on four threads) is below the drive's sequential rating, as expected for ~11 MB random reads. **Plausible**, but sensitive to workload drift away from the calibration traffic, and the figures are "first request after start" on a code prompt.
- 128 GB prefill ≈ 120 tok/s: one layer-major pass must read the whole streamed tier (50.52 GiB ≈ 54.2 GB) ≈ 12 s at 4.5 GB/s, or ≈ 17 s at the logged 2.95 GiB/s. The 3,981-token prompt took ≈ 33 s, and the 21,420-token prompt ≈ 182 s (≥ 2 passes of ≤ 16,384 tokens ≈ 24-34 s of SSD). The rest is compute without bounded replay (≈ 32 GFLOP/token ≈ 3.8 TFLOPS) on a path Lucebox itself says "uses only a small part of what the R9700 can compute". **Plausible.**
- TTFT arithmetic matches the claims. Without the R9700: 30,000/340 + 256/16 ≈ 104 s ("almost 2 min"). With it: 30,000/1,000 + 256/33 ≈ 38 s ("about 40 s").
- Load time: ≈ 120 GB at the drive's 7.1 GB/s rating is ≥ 17 s, and "under a minute" needs ≥ 2 GB/s average. **Plausible.**
- Comparison caveats: the "3x / 2x" compare different engines, different 2-bit files (ROCMFP2S vs antirez Q2; KL 0.266 vs 0.260, so similar fidelity) and different prompt shapes (2K at depth vs whole prompt; Lucebox's "32K" point is measured at 25.4-30.8K). Both sides use DSpark and bounded replay. The 192 GB side also uses a per-box router bias, which changes which experts are selected relative to the reference model; Framework's side does not.
- Quality-relevant facts: ROCMFP2S, the file behind every speed number, agrees with the original FP4 checkpoint's top-1 token only 77.7% of the time (KL 0.266, ppl 9.59 vs 8.45). No hard-bench score is published for ROCMFP2S itself. The best quality figure (164/177) is for a different file (`ds41-lucebox-final.gguf`) in "exact" mode (plain greedy, no drafter, no Lucebox profile). With the Lucebox profile + DSpark the same file scored 158/177. Lucebox attributes the gap mainly to the 16K-token answer limit, and it is not isolated from the router bias.
- Relevance to A.T.L.A.S. (analysis only): the Principal's node equals the "without the R9700" configuration. Published performance there is Framework's ≈ 14 tok/s plain / ≈ 16 tok/s with DSpark and ≈ 300-360 tok/s prefill using DwarfStar + antirez Q2 (main weights ≈ 151.8 GiB per the GGUF header, Engram left on disk). Lucebox's ROCMFP2S main weights (158 + 8 = 166 GiB, plus drafter) exceed the node's ≈ 164 GiB engine budget. The Lucebox engine is HIP/ROCm-only for these profiles, and its V4.1 profiles assume an R9700 as `hip:0`.

## Key question 5: Related techniques and prior art — what is standard and what is novel

### Takeaway
Each building block has prior art: hot/cold placement by activation frequency, computing experts where they live, expert caches with next-layer prefetch, SSD/flash streaming, cache-aware routing bias, layer-major batched prefill, and lossless self-speculative decoding. What is distinctive is the combination on consumer AMD hardware: one HIP process driving two different GPU architectures (discrete RDNA4 gfx1201 + APU RDNA3.5 gfx1151) as co-owners of the same MoE layer with on-device joins. A third SSD owner sits inside one fused decode graph through a host mailbox, alongside per-box offline placement plus static router bias and protected experts, custom 2.5-bit sign-flip codebook formats, and exact (bit-identical) speculative verification.

### Cited Findings
- llama.cpp static placement: "`-ot, --override-tensor <tensor name pattern>=<buffer type>,...` | override tensor buffer type"; "`-cmoe, --cpu-moe` | keep all Mixture of Experts (MoE) weights in the CPU"; "`-ncmoe, --n-cpu-moe N` | keep the Mixture of Experts (MoE) weights of the first N layers in the CPU". — [llama.cpp server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) (fetched 2026-10-15). An issue commenter (Aug-Sep 2026) calls `--n-cpu-moe` "a very blunt version of tensor overri[des]" — [llama.cpp #27501](https://github.com/ggml-org/llama.cpp/issues/27501) (via earlier notes `strix_halo_capacity_performance.md`)
- PowerInfer (Dec 2023): exploits "a power-law distribution in neuron activation ... a small subset of neurons, termed hot neurons" placed on the GPU, cold on the CPU. — [arXiv 2312.12456](https://arxiv.org/abs/2312.12456)
- Fiddler (Feb 2024): "CPU-GPU Orchestration for Fast Inference of Mixture-of-Experts Models", "strategically utilizes CPU and GPU resources by determining the optimal execution strategy" (computing experts on the CPU instead of moving weights). — [arXiv 2402.07033](https://arxiv.org/abs/2402.07033)
- KTransformers: CPU/GPU hybrid MoE inference with "CPU-GPU Expert Scheduling" (Jan 22, 2026) and "DeepSeek-V4-Flash on a single Ascend NPU with CPU expert offload" (Aug 16, 2026). — [KTransformers README](https://github.com/kvcache-ai/ktransformers) (fetched 2026-10-15)
- Eliseev & Mazur, "Fast Inference of Mixture-of-Experts Language Models with Offloading" (Dec 2023): offloading strategy "taking advantage of innate properties of MoE LLMs" to run Mixtral-8x7B on desktop hardware. The paper's LRU expert cache and speculative next-layer expert loading are from my knowledge of the paper, not the abstract read here. — [arXiv 2312.17238](https://arxiv.org/abs/2312.17238)
- MoE-Infinity (Jan 2024): "Sparsity-Aware Expert Cache"; on batch-1 personal machines "a small number of experts are frequently reused". — [arXiv 2401.14361](https://arxiv.org/abs/2401.14361)
- ProMoE (Oct 2024): "a novel proactive caching system that utilizes intermediate results to predict subsequent expert usage. By proactively fetching experts in advance, ProMoE eliminates passive cache misses"; 2.20x prefill / 2.07x decode average speedups. — [arXiv 2410.22134](https://arxiv.org/abs/2410.22134)
- Pre-gated MoE (Aug 2023): algorithm-system co-design for MoE inference. — [arXiv 2308.12066](https://arxiv.org/abs/2308.12066)
- HOBBIT (Nov 2024): "A Mixed Precision Expert Offloading System for Fast MoE Inference". — [arXiv 2411.01433](https://arxiv.org/abs/2411.01433)
- EdgeMoE (Aug 2023): on-device MoE inference engine. — [arXiv 2308.14352](https://arxiv.org/abs/2308.14352)
- Mixture of Cache-Conditional Experts (Nov 2024): "a novel cache-aware routing strategy that leverages expert reuse during token generation to improve cache locality ... 2× speedups on mobile devices ... training-free". — [arXiv 2412.00099](https://arxiv.org/abs/2412.00099)
- Apple, "LLM in a flash" (Dec 2023): running LLMs "that exceed the available DRAM capacity by storing the model parameters in flash memory". — [arXiv 2312.11514](https://arxiv.org/abs/2312.11514)
- Flash-MoE (2026): a C/Metal engine running Qwen3.5-397B-A17B on a 48 GB MacBook Pro by streaming experts from SSD, ≈ 4.4 tok/s, relying on the OS page cache (≈ 71% hit rate). — [lilting.ch article](https://lilting.ch/en/articles/flash-moe-qwen35-397b-metal-inference), [insiderllm guide](https://insiderllm.com/guides/flash-moe-run-397b-model-laptop/) (excerpts; original repository not confirmed)
- FlexGen (Mar 2023) and MoE-Lightning (Nov 2024): throughput-oriented offloading that schedules computation to reuse weights across many tokens. This is the same idea as reading each streamed expert "once per pass instead of once per chunk". — [arXiv 2303.06865](https://arxiv.org/abs/2303.06865), [arXiv 2411.11217](https://arxiv.org/abs/2411.11217)
- Engram (DeepSeek, Jan 2026): "its deterministic addressing enables runtime prefetching from host memory, incurring negligible overhead". This is the design basis for leaving Engram tables off-GPU. — [arXiv 2601.07372](https://arxiv.org/abs/2601.07372)
- DwarfStar (antirez's engine) already ran V4.1 on a single APU with main weights in memory and "Engram tables on disk", and supports SSD streaming of main weights ("On Strix Halo, it must either stream some of the main weights from SSD, which is slow, or split them across two nodes"). DSpark "cannot be combined with SSD streaming" there. — [Framework blog](https://frame.work/blog/what-192gb-changes-for-local-ai-on-the-framework-desktop)
- Lucebox's cluster work credits prior community work: "It started from maikzz32's work on Strix Halo clusters, which already ran DeepSeek V4 Flash across boxes over RoCE." — [cluster post](https://www.lucebox.com/blog/lucebox-cluster-nic)
- Lucebox's own V4 description of the design choice: "Asymmetric expert parallelism means the two GPUs are assigned different work rather than equal slices of every operation." The V4 tests used "four routed experts per token" (reduced from six), and "comparison with the six-expert reference configuration was outside the scope". — [V4 asymmetric post](https://www.lucebox.com/blog/deepseek-v4-asymmetric-parallelism). For V4.1 the docs give "384 / top-6", and no top-k reduction appears in the ds41 profiles. — [DS41.md](https://github.com/Luce-Org/lucebox/blob/main/server/docs/DS41.md), [launch_profiles.h](https://github.com/Luce-Org/lucebox/blob/main/server/src/server/launch_profiles.h)

### Inferences
- Standard (has clear prior art): frequency-ranked static hot/cold placement (PowerInfer; llama.cpp `-ot` done by hand); computing experts on the device that stores them instead of copying weights (Fiddler, KTransformers), with an iGPU taking the CPU's role here; a slot cache for SSD experts with next-layer prediction and prefetch (Eliseev & Mazur, ProMoE, MoE-Infinity); SSD/flash weight streaming (LLM in a flash, Flash-MoE, DwarfStar); biasing the router toward cached experts (Cache-Conditional Experts); layer-major batching to amortise weight reads (FlexGen, MoE-Lightning); self-speculative decoding with the model's own MTP/DSpark head; Engram left in host memory or on disk (DeepSeek's own design and DwarfStar's practice).
- Distinctive in Lucebox's implementation (from their docs; I did not find an identical public system in the sources read): (a) one process and one HIP binary driving a discrete RDNA4 and an APU RDNA3.5 GPU as simultaneous owners of disjoint expert sets in the same layer, with the join on the R9700; (b) a third "streamed" owner inside the same fused decode/verify graph via a host-mapped mailbox and resolver thread; (c) per-box fitted placement plus a static, offline per-expert router bias plus "protected" massive experts that keep their unbiased selection; (d) the iGPU tier extended past its carve-out into mlock'ed host memory; (e) custom 2.5-bit ROCMFP2 formats with a sign-flip ("mirror the codebook") bit; (f) bit-identical speculative verification with batch-invariant products; (g) a pipelined layer-major prefill in which the R9700 runs attention for band n+1 while the iGPU runs experts for band n.
- Trade-offs that follow from the cited facts: the router bias and close-call tie-breaking toward fast-memory experts make output depend on the box's placement (the cluster post: "Two boxes don't give exactly the same answer as one box ... the router breaks close calls differently, since each setup has its own placement"). "Bit-identical" therefore refers to speculative vs plain decoding under the same profile, not to the reference model's routing.

### Gaps
- No peer-reviewed paper or formal write-up from Lucebox. The prior-art comparison above is my mapping. A systematic search for an identical dGPU + APU-iGPU expert-parallel system was not done beyond the sources listed.
- The original Flash-MoE repository and its exact numbers were confirmed only through secondary articles (excerpts).
- KTransformers' paper venue and details were not re-read this session; only the README news items were.
